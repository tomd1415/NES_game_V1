1. The big picture

NES Studio is a browser game-maker: a pupil draws 8×8 tiles, builds a level, picks rules and presses Play, and a small Python server turns the project into C and 6502 assembly, compiles it with cc65 and sends back a real .nes ROM that runs in the page. Between April and September 2026 it grew from a Zelda II-style demo into an eight-mode Studio with a versioned engine (v84 on this branch). Most of what it taught me was about the NES's tiny timing budget, and about tests that were green for the wrong reason.

It began on 9 April (7d3afae) as one cc65 program with a jumping player, became five C "steps" for pupils to edit in VS Code, then a set of browser pages ending in a Builder that assembles a game from ticked modules. There are no commits in May; June went on pupils' bug reports and a rebuilt code generator. July carried 598 of the 1,008 commits: the unified Studio (73cecdd), engine versioning (v1 on 5 July, b76f54c), an SMB-style engine, hand-written 6502 and a native Linux app on this branch. August was almost all verification, and main was merged in on 2 September (d3d507f). 707 commits carry a Claude co-author line, so several lessons are about checking AI sessions' confident claims.

Where it stands: this branch is 284 commits ahead of main and 2 behind, and not merged. Those two commits are main's own engine v80 (391d262, 10 September), a different engine from this branch's v80.

The one-line summary The NES lets you touch the picture for only a sliver of each frame, and an emulator or a test suite can look perfect while that rule is broken. The project worked when each claim was checked against something that could say no: FCEUX as well as jsnes, a planted fault as well as a passing suite, the bytes as well as the hash.

2. How the NES draws a picture

Everything in the Studio is shaped by the NES's picture chip, the PPU (the "NES Architecture Summary" in docs/guides/TEACHER_GUIDE.md; docs/design/design-principles.md §2).

Tiles and CHR. The NES never stores a screen as pixels. Pixels exist only inside tiles: 8×8 squares in which each pixel is a 2-bit number, 0 to 3, that picks a palette slot rather than a colour. A tile is 16 bytes in two bitplanes: 8 bytes holding bit 0 of every pixel, then 8 holding bit 1 (tools/chr_codec.py). The tile store is the CHR: here one 8 KB bank with sprite tiles at $0000 and background tiles at $1000, selected by bit 4 of PPU_CTRL (build_chr in tools/nes_studio_core/graphics.py).

Nametable and attributes. The background is a nametable: 32×30 tile numbers plus 64 attribute bytes that choose palettes, 1,024 bytes in all, exactly a .nam file. A background palette applies to a whole 16×16-pixel quadrant, not to one tile. The original editor stored a palette per 8×8 tile, which docs/design/target-data-model.md calls "a compile-time lie to remove". 16×16 blocks (metatiles) with one palette each make the honest answer the easy one.

Palettes. There are 64 fixed colours. A game picks one backdrop plus four background and four sprite palettes of three colours each, 32 bytes at $3F00. Pixel value 0 in a sprite is transparent.

Sprites and OAM. Sprites are 64 four-byte entries (Y, tile, attributes, X) in a 256-byte table, OAM. The engine fills a shadow copy at $0200 and copies it in one go by writing to $4014 (OAM DMA). At most 8 sprites show on one scanline, and Y = $FF hides one. A big character is a grid of sprites, so an 8×8-tile player uses all 64.

Verified: a nametable byte is a tile number, not a letter Dialogue showed garbage on projects whose pupil had not painted a font, because the engine wrote ASCII codes into the nametable and those tile numbers held scenery (finding N3 in the architecture review). The server now seeds a built-in font into blank background tiles whenever dialogue is on (_seed_dialogue_font, f89d778, 18 June).
Everything references shared tiles On the hardware a block is four tile references and a character is a grid of them, so editing a tile changes it everywhere and "CHR 214/256" is a real budget (design-principles.md §3). The design keeps that visible, with an "also used by…" warning and Duplicate first, on the rule that a tool which lets a pupil build what the hardware cannot do "is teaching a lie".

3. From the browser to a ROM

What happens when a pupil presses Play (the /play contract in TEACHER_GUIDE.md, and §1 of the review):

A server is needed because cc65 is a native toolchain and the editor cannot POST from a file:// page. Builds run in parallel under BUILD_SEM (2 to 8 at once), which replaced a single lock "because serialising every build is a bottleneck when thirty pupils press Play at once".

Fat engine, thin data. The June review found the bugs clustered where Builder modules emitted per-frame C loops as strings, while the subsystems already compiled into the engine behind #if flags (movement, Player 2, the HUD) were sound. The direction chosen: modules emit #defines and constant tables, not control flow. The review also rejected a full assembly rewrite, because for a teaching tool "C is the feature": pupils read and edit the main loop.

Trap: untracking generated files broke the baseline Playtests used to rewrite engine sources inside the repo, so I untracked the eight generated files. That broke the golden-hash checks, which build that folder with make directly: once a playtest overwrote the untracked copies, make built the wrong ROM. They were re-tracked the same day (230fdce), and the commit names the real fix, building in a temporary directory, which is what happens now. If engine sources show as modified after a Play, something is genuinely wrong.
Verified: the one-byte overflow The server turns ld65's "segment overflows" error into "your game is about N bytes too big". ld65's format string is by %lu byte%c: an s for a plural, a space for exactly one. The regex required bytes, so a one-byte overflow showed the child the raw linker error. The fix was one character, bytes?, with a test seen to fail first (d90f10b).

4. The engine and its version contract

The engine is everything that turns a project into a ROM: the C templates, the assembler, the cc65 project and the server's code generator. The contract (CLAUDE.md; docs/design/engine-versioning.md): any change that could alter ROM output means bumping tools/engines/ENGINE_VERSION and engine-version.js to the same integer, adding a CHANGELOG entry and freezing a snapshot with node scripts/snapshot-engine.mjs. run-all.mjs fails if the constants disagree or the snapshot has drifted, and new projects are stamped with state.engineVersion.

Off by default keeps the golden ROMs still. New behaviour sits behind a flag that is off unless a project needs it, so the preprocessor and cc65 strip it from every other project and their ROMs stay byte-identical. The proof is one line of run-all.mjs: GOLDEN_STOCK = '1730448e…', pinned on 20 June (a793bd1), is still the value at v84. All 84 engine versions came after it.

Snapshots, and what they do not do. Each version is frozen into tools/engines/v<N>/ with a SHA-1 manifest. Two things surprised me in the record. The snapshot script reads committed bytes, so snapshotting before committing silently freezes the previous engine, --check agrees with itself, and because snapshots are immutable the only way out is another version (tools/engines/README.md). And nothing builds from a snapshot yet: the server's _resolve_engine_versions is "still provenance-only", every build uses the current sources, and "the selection step itself is simply unbuilt". A project stamped v63 builds with today's templates, which is why fixtures labelled "v63" had drifted for twelve versions (LESSONS-LEARNT.md §4).

Verified: two eras of snapshot Up to v75 a snapshot held 19 to 30 files and no Python, though the Python code generator produced most of the ROM, so a codegen change could not turn the gate red (finding F7). This branch's v76 added tools/nes_studio_core/ (41 files), but the merge took main's Python-less v76–v79, so today only v80–v84 cover the codegen. That is why the README defines the boundary by what a manifest lists, not by a version range.
Trap: two branches, one counter While this branch and main were apart, each published its own v76, v77 and v78. Main's had shipped to classrooms, so at the 2 September merge main kept those numbers and this branch's engines were renumbered v80–v83, with the superseded CHANGELOG entries kept and struck through (d3d507f). A gate now compares the collision set with a recorded list in tools/engines/main-manifests.json. Then on 10 September main published its own v80 (391d262). The two v80/manifest.json files differ (checked 2026-10-06), and the recorded list, taken from main at 1c399c0, predates it. Same collision, one number later.

5. Timing on a 1.79 MHz machine

The PPU is drawing almost all the time. The CPU can safely write to it only during vblank, the gap between frames: about 2,273 CPU cycles, of which the sprite DMA uses 513, leaving room for roughly 160 bytes to $2007 (review finding N5). A plain cc65 loop costs 50–65 cycles per byte and an unrolled lda buf+N / sta $2007 pair costs 8 (LESSONS-LEARNT.md §5). Anything bigger has to be prepared while the picture draws, then copied fast or spread over several frames.

The write that vanished. In April a scrolling level smeared stripes across the background. FCEUX's PPU viewer showed each new column being laid along a row. The note in dad85a2 blames cc65 for dropping the PPU_CTRL write that sets column stride, because a later assignment to the same address followed. The fix was to declare every PPU register macro volatile. jsnes had not shown the fault: the note says glitch detection on jsnes "isn't meaningful when jsnes already tolerates the timing our ROM used to have".

The dialogue box that blanked the screen. Pupils reported the stage "glitches for a split second" when an NPC's box opens (#31). The banner was 128–256 writes in one vblank with rendering off, so the burst ran into the visible frame. The fix copies the scroll streamer's pattern: prepare one 32-byte row per frame, then copy it in vblank with an unrolled burst of about 260 cycles (a70241e, main's v78; v82 here). A new test counts lit pixels in a 40-scanline band: 7,680 → 0 on the opening frame before, 7,680 throughout after. An earlier plan had deferred it as "Verification: visual, needs Mesen".

The status bar that would not keep still. The SMB-style status bar stays put while the level scrolls: the engine places an opaque sprite 0 at the bottom of the strip, polls the sprite-0 hit flag (bit 6 of PPU_STATUS), and at the hit writes the playfield's scroll. It flickered after the first screen. Driving it from the NMI was reverted because jsnes showed garbage (a91a23f). v69 (8446e27) trimmed vblank cost instead, measured as flicker-free on runs with no enemies. Re-measured with enemies, the flicker was dropped frames, so v70 (6c65967) went back to the NMI with four fixes. A double buffer stops the NMI copying a half-built OAM. The NMI-enable bit had never been set. The main loop waited on $2002, and reading $2002 clears the vblank flag, which raced the NMI's own poll. And the poll is now bounded. In FCEUX, frames showing sky fell from 211 to 3.

Trap: the emulator in the browser is not the hardware jsnes "does not model the 8-sprite-per-scanline limit or sprite-0-hit timing", which is "why the tests stay green while the flicker is real on hardware/FCEUX" (docs/design/2026-07-08-smb-bg-status-bar.md). The headless tests run in jsnes, so timing claims needed FCEUX or Mesen.
Trap: the optimiser "regression" was a test sampling mid-fall The first time I switched cc65 to -Os, two render tests failed, and I reverted it as "a visual bug that would have shipped to pupils" (89cf371). The same day, tracing the player's position showed nothing was miscompiled. -Os finished loading the world about 45 frames sooner, so tests that sampled at a fixed frame caught the player mid-fall. They were changed to wait for him to settle, and -Os went in (a793bd1).

Hand-written 6502, one function at a time. asm-lab/ rewrote engine functions individually, each passing three gates: correct (a unit harness in a real ROM, checked against the C and an independent JavaScript model), integrated (the render suites still pass), and efficient (no bigger or slower than cc65 -Os). world_to_screen_x went from 66 bytes and about 120 cycles to 20 bytes and about 28 (asm-lab/STATUS.md). By v54 (df78e76, 9 July) "every per-frame hot loop is on ASM".

Trap: an 8-bit cursor and a 256-byte table The assembly draw_player kept its OAM position in the 8-bit Y register. An 8×8-tile player fills exactly 256 bytes, so the final store wrote 256 mod 256 = 0. The player drew correctly, but everything drawn after him saw an "empty" table and drew on top, and their oam_idx > 252 guards never tripped: pupils saw "random mess on screen" (#37). The writes are fine at exactly 256 but the cursor is not, so the fix tests a strict base + W×H×4 < 256 (fa79846; v80 here).
Trap: "parked" was a coordinate An enemy that was off-room or defeated was parked at Y = 0xFF, and guards tested >= 0xEF at some sites and >= 240 at others. In a two-screen-tall level a real Y runs to 479, so enemies in the lower half neither moved nor hurt anyone while looking correct. Main's v80 makes "parked" an all-ones value tested by equality, leaving no threshold to spell two ways (391d262).

6. Making it work for pupils

Two front doors. The first (15b1616, 12 April) was a VS Code workspace in which everything except **/src/main.c is read-only, Ctrl+Shift+B builds and runs, and // TRY: and // EDIT: comments point at things to change. That suits pupils who already read C; the browser editor was for everyone else.

The Studio replaced seven loosely connected pages with one workspace: a mode rail, an editing dock, the game running on a "TV", and a quest log. Its principles (design-principles.md): boot into a working starter game, never a blank canvas (there are eight, the document citing pupils' "I don't know how to start" paralysis); teach by doing, with a self-ticking quest log and a "Needs attention" list with Fix → jumps instead of intro dialogs pupils skipped; autosave, snapshots and a Time Machine so work is very unlikely to be lost; and Beginner, Maker and Advanced levels that reveal more of the eight modes, with locked modes still visible. The test for any control: "Could a confused KS3 pupil ignore this control and still finish a game?"

Pupils as the bug tracker. An in-editor feedback form went in on 22 April (cbac562). Its 25 entries were transcribed on 17 June, and teacher-collected reports became a numbered list in docs/feedback/recently-observed-bugs.md, now 39 items. Several engine versions exist because of a pupil report: the dialogue flash (#31), the "random mess" (#37), and a door that showed the wrong background on a room's second screen (#2, v63).

Verified: a frozen game nobody could see failing For #37, the browser's emulator loop had no error handling. An exception inside nes.frame() does not stop a setInterval, so a fault re-threw 60 times a second into a console no pupil opens while the game sat frozen. It now has try/catch, a frame watchdog and a plain-language banner with a retry (STATUS.md).

Accounts are optional and minimal: a username that is not a real name and a scrypt-hashed password, no email, no analytics. The native app on this branch is a PySide6 sibling held to the web version by contract tests. Its emulator wraps tetanes-core, chosen because it is MIT or Apache licensed where the mature cores are GPL, it produces audio, and it builds to a self-contained wheel, so "target machines need no Rust, no compiler and no apt packages" (native/nes_core/README.md).

Trap: a green suite and a blank app The native suite was once fully green while the app showed a transparent emulator frame and a white-on-white panel, and crashed on every background switch. Every test asserted document.field == X and none asserted that anything had been drawn. The rule now: assert pixels, not document fields (native/README.md, "Six traps").

7. Tests that were green for the wrong reason

There are three suites: Node builder tests that compile real ROMs and run them headless in jsnes, Playwright for the Studio, and pytest for the native app. August's verdict (docs/guides/what-the-gates-prove.md): "The repeated failure on this branch has not been gates going red. It has been gates being green for the wrong reason."

The render harness (Arc A, June) boots a compiled ROM in jsnes inside Node and asserts on what was rendered, not just that the C compiled. Before it, the "byte-identical" check built the template with no modules, so that check never compiled any module's output (review smell S2). It was re-founded on frozen golden hashes (680833b).

Trap: a guard that could not fail "PPU register macros are volatile" had been green since it was written. Its regex matched the old spelling *((unsigned char*)0x20XX), but with volatile removed today's macros read (*(unsigned char*)0x2006), which it never matched. It was found by planting the exact fault and watching the suite stay green (cb19d8e). The same day every invariant in run-all.mjs was given a planted break: "24 breaks, 24 caught" (cff3cdd).
Trap: a test any canvas would pass A Studio test checked that the full-screen preview "opens a modal with a canvas", while the preview always showed the level's top-left screen. The fix asserts something only correct behaviour produces: the canvas is as wide as the level, 1,024 device pixels for two screens against 512. With the bug restored, the new test went red and the old one stayed green (LESSONS-LEARNT.md §1).
Trap: a meta-test one value out The plan for #14 said "flip the threshold to 239 and the tall-project assertion must go red". It did not: the fixture's enemy was at y = 400, which both the right and the off-by-one threshold reject. Only an entity at exactly 239 tells them apart (LESSONS-LEARNT.md §1).
Trap: reasoning about hashes instead of reading bytes Regenerating seven starter fixtures changed every project hash, and I reported that the starters had drifted. A decompress-and-diff showed the inputs differed only by a timestamp. "A hash tells you two things differ; only the diff tells you what." The tell was the uniformity: real drift would not hit all seven (LESSONS-LEARNT.md §4).
Verified: not flaky, under-budgeted Two Studio tests that failed under load were waved through for weeks as "the box was busy". On a quiet machine they took 13.8 s and 9.8 s, against 3.6 s for the next slowest and a median of about 1 s, with a 30 s limit. It was always the same two (ea2fdfe; LESSONS-LEARNT.md §3).

9. More traps

Trap: a fix on a branch that was never merged 945393e (26 June) added an oam_idx > 252 bound to the C Player 1 sprite loop. It exists only on origin/fix/br-03-oam-overflow, which was never merged, and the fix plan already marked BR-03 fixed. A month later the #37 investigation found that loop "had no bound at all" (fa79846).
Trap: the answer was one branch away I spent two stretches getting a port count wrong, then found the lesson that would have prevented it already written in main's lessons file and its TEST-SERVERS.md, neither of which existed on this branch. The cheap check is git log --oneline HEAD..origin/main before an audit: "A branch that has not merged its trunk in weeks is not a snapshot of the project; it is one opinion about the project" (LESSONS-LEARNT.md §6).
Trap: tools that fail quietly An awk script using strtonum printed nothing on Debian's mawk, and that became "nothing is listening on 8765" while the server ran. Playwright and three builder suites shared port 18790, and the server, finding one already running, said "nothing to do" and exited 0. And git add silently declines a path .gitignore matches, which is how seven baseline ROMs and a whole .devcontainer/ went uncommitted (LESSONS-LEARNT.md §1–2).

10. General lessons

Ask a check what it would reject "A canvas is visible" and "the regex matched" are true of the working version and of most broken ones. Plant the fault and watch the check go red before trusting its green. Then ask the other question: could it fail when nothing is wrong? A gate that cries wolf gets deleted with its coverage.
"Needs a human to look" is a claim to test once The dialogue flash turned out to be countable headless. Some things really do need a person (the event sounds need ears, after inspecting jsnes's audio proved too fragile), but that was tried first.
Know what your emulator does not model jsnes skips the 8-per-scanline limit and sprite-0 timing, and it tolerated a scroll fault that FCEUX showed plainly. Use the convenient tool for bytes and behaviour, and a faithful one for timing.
Gate new behaviour off by default Because each feature compiles out unless a project asks for it, one golden hash has guarded the no-module ROM through 84 engine versions. That is what made a fast-moving engine safe to change.
A number two people allocate will collide Engine versions were integers handed out independently on two long-lived branches, and they collided twice. Anything that must be unique needs one writer, or names that cannot clash.
If two lists must agree, derive one A hand-written list of modules to syntax-check had silently missed 18 of 32. Enumerating the directory at run time removed the second list instead of policing it. Documentation is not a check.

11. Test yourself

What is in a 16-byte NES tile, and why can a tile not say "red"? An 8×8 grid of 2-bit values in two bitplanes. The values 0–3 pick a slot in whichever palette the tile is drawn with; the attribute table or the sprite's attribute byte chooses that palette.
Why could the old editor's per-tile palette never be honoured in the ROM? The attribute table chooses a background palette per 16×16-pixel quadrant, so four tiles must share one. 16×16 blocks with one palette each make that true by construction.
Dialogue showed garbage on some projects. Why, and what fixed it? A nametable byte is a tile number. The engine wrote ASCII codes, and without a painted font those tile numbers held scenery. The server now seeds a built-in font when dialogue is on.
Why does the dialogue fix prepare one row per frame instead of writing the whole box at once? Vblank is about 2,273 cycles, 513 already used by OAM DMA. The whole banner was 128–256 writes with rendering off and ran into the visible frame. One 32-byte unrolled row takes about 260 cycles and fits.
An 8×8-tile player drew correctly, yet everything after him drew on top. Why? 64 sprites × 4 bytes = 256. The assembly kept the OAM cursor in the 8-bit Y register, so it wrapped to 0; later writers saw an empty table, and their "> 252" guards never fired.
The main-loop status bar was measured at zero flicker. Why was that not good enough? The runs had no enemies. With enemies, game logic overran vblank and frames dropped. And jsnes could not judge it, because it does not model sprite-0-hit timing.
Why did waiting on $2002 in the main loop hang the NMI-driven status bar? Reading $2002 clears the vblank flag, so the main loop raced the NMI's own sprite-0 poll of that register. The loop now waits on a flag the NMI clears.
The first -Os build failed two render tests. Why was reverting it the wrong conclusion? Nothing was miscompiled. -Os loaded the world about 45 frames sooner, and tests sampling at a fixed frame caught the player mid-fall. Waiting for him to settle fixed them.
A project is stamped engineVersion: 63. Which engine builds it today? The current one. The target is recorded for provenance only; building from tools/engines/v63/ is designed but not built.
Why must you commit before running snapshot-engine.mjs? It reads HEAD. Snapshot first and v<N>/ freezes the previous code, --check agrees with itself, and snapshots are immutable, so the only fix is another version.
A meta-test put an enemy at y = 400 to check a 238/239 threshold. What was wrong with it? 400 is rejected by both the right and the off-by-one threshold, so the test could not tell the bug from the fix. Only a value exactly at the boundary separates them.
Two Playwright tests failed only "when the box was busy". What showed they were genuinely wrong? It was always the same two; real noise moves around. Measured quietly they took 13.8 s and 9.8 s against a median of about 1 s, so they were under-budgeted.

13. Glossary

PPU
The NES's picture chip: draws 256×240 pixels at 60 frames a second from tiles, nametables, OAM and palettes, through registers at $2000–$2007.
CHR / pattern table
The tile graphics; here one 8 KB bank with 256 sprite tiles at $0000 and 256 background tiles at $1000.
Bitplane
One bit of every pixel stored together; an NES tile is two 8-byte bitplanes.
Nametable
A 32×30 grid of tile numbers forming the background, plus its 64-byte attribute table.
Attribute table
Bytes choosing a background palette for each 16×16-pixel quadrant.
Metatile (block)
A 2×2 arrangement of tile references with one palette.
OAM
64 sprites × 4 bytes (Y, tile, attributes, X), copied from a RAM shadow by OAM DMA (a write to $4014, 513 cycles).
Vblank
The gap between frames, about 2,273 CPU cycles, when the CPU can safely write to the PPU.
NMI
The interrupt the PPU raises at the start of vblank when bit 7 of PPU_CTRL enables it.
Sprite-0 hit
A flag (bit 6 of $2002) set when sprite 0 overlaps an opaque background pixel; used to time a mid-frame scroll change.
NROM (mapper 0)
The simplest cartridge: 32 KB of program, 8 KB of CHR, no bank switching.
cc65 / ca65 / ld65
The 6502 C compiler, assembler and linker.
jsnes, FCEUX, Mesen
NES emulators: jsnes runs in the browser and the headless tests; FCEUX and Mesen are more faithful and were used for timing.
Engine snapshot
A frozen copy of one engine version's sources under tools/engines/v<N>/, with a SHA-1 manifest.
Golden hash
The pinned hash of a reference ROM; a change says the bytes differ, and only a diff says how.
Mutation testing
Planting a deliberate fault to prove a test or guard goes red when it should.
Sentinel
A special value meaning "none" or "parked", such as Y = 0xFF; safe only if no real value can equal it.
